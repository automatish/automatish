How I approach QA

Four working principles, and what each one looks like in practice.

01

Build the framework so it survives the product, not just the release

Frameworks I've built — from a Cypress suite built from scratch for an automotive OTA platform to a legacy trade-pricing regression suite — are meant to be maintained by whoever inherits them, not just by me.

02

Domain risk decides what gets automated first

In payments and banking, some failures are compliance incidents, not just bugs. Coverage priority follows what the business actually loses when something breaks, not just what's easiest to script.

03

A dashboard is only as trustworthy as the checks behind it

Customer-facing dashboards fail quietly — the data looks fine until it isn't. I test the pipeline feeding the dashboard as carefully as the UI on top of it.

04

Own the strategy, not just the tickets

Test planning, test strategy and process setup have been part of my remit at several companies, alongside interviewing and onboarding other QAs — deciding what to test is as much the job as testing it.
